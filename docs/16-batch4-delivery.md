# 第四批：SQL 相册、版本化缓存和实测 ANN

2026-09-05；基于 d2983f1 加前三批工作树。只修改本地后端、测试、基准和文档，未提交、部署或调用付费模型；无新增迁移。

## 已完成

相册混合评分下推 SQL，包括余弦语义分、时间衰减、标签亲和度、用户风格向量及归一权重；只读取照片展示和版本检查所需列，照片向量不再传回 Python。一般语义检索保留候选上限；评分已在 SQL 完成，Python 仅对有界候选稳定排序。SQL 评分对空向量、零向量、未来日期和画像去重做了回归；数值按数据库精度舍入，不承诺所有浮点临界值与 Python 位级一致。

`/search/album-fallback` 的综合排序现在对相册范围先评分再分页，修复“先取语义前300再做综合排序”遗漏高新鲜度候选的问题。Agent 时间线浏览也使用 SQL keyset：综合排序用最终分数/ID，时间线用拍摄时间/ID（NULL 最后）。每页最多100条、SQL精确 count 与当页同一语句读取，不受语义候选300条上限约束。评分时间、查询向量与用户画像冻结在计划上下文，翻页不再请求 embedding。

相册是带插入时间边界的实时窗口：每页重新检查归属、过滤和更新时间，计划创建后的编辑被跳过，需要新搜索重新纳入；删除会反映到下一页 count。它不是跨请求 MVCC 快照，因此不声称 `result_set_complete=True`。`total_matches` 是该页语句可见窗口的精确计数，可能随删除/编辑变化。v4 keyset 游标仍签名、绑定用户与计划；语义结果继续使用第三批快照游标。

parser、embedding、文本核验和视觉核验共用 `search_cache.py`。缓存键包含阶段、用户范围、模型/供应商、提示或解析版本和 `SEARCH_CACHE_REVISION`；parser 额外绑定时区/本地日期，文本证据绑定照片内容版本，视觉包含内容哈希和存储键。照片签名URL不写入缓存；读取会验证向量形状和核验结构。旧 namespace 自然过期，不全局清 Redis。独立于搜索预算调用的 parser 保留原有行为，只有 SearchService 内的模型解析使用共享缓存。

Redis singleflight 按相同计算键跨 API/Worker 争抢令牌，只有持有者启动模型工作；等待者命中结果后不预留模型调用额度。独立计划仍保留各自预算，同一计划仍按第三批防并发写入。等待者取消不取消持有者；持有者取消释放租约，其他请求可接手；写缓存和释放都校验令牌。失败仅保留2秒脱敏错误标记，避免故障时并发重试洪峰；预算拒绝不共享为供应商失败。不启动脱离请求生命周期的后台模型任务。模型调用已经开始后被取消，其实际供应商费用仍可能发生，不保证外部服务 exactly-once。

## 本机合成实测

[原始结果](benchmarks/batch4-search.json)包含 `EXPLAIN (ANALYZE, BUFFERS)`；[运行输出](benchmarks/batch4-run.txt)。PostgreSQL16.15、pgvector0.8.6、Redis7，6000条1024维归一随机向量，种子4092026，用户规模3000/300/30/2670。相册测3000条、返回20条，权重0.4/0.35/0.25，无用户画像；固定评分时刻，SQL与全量参照Top-20一致。第三批语义短名单与该全量综合排序Top-20仅有5%重合，这是合成排序用例，不是实际模型检索准确率。

| 路径 | 中位耗时 ms | 样本最大值 ms | Python 分配峰值 MB |
|---|---:|---:|---:|
| 第三批：候选完整 ORM + Python 排序 | 180.50 | 258.52 | 6.505 |
| 全量 ORM 精确评分参照 | 1454.86 | 1496.32 | 63.562 |
| 第四批：SQL 候选评分（最多300） | 81.79 | 89.59 | 0.715 |
| 第四批：实际相册 keyset 页（20条 + count） | 98.27 | 111.12 | 0.353 |

每个路径先预热，再测5次；JSON中的 p95_ms 使用这5个样本的最大值，不能据此推断生产p95。内存用 tracemalloc 单独采样，是Python分配峰值，不是进程RSS或数据库内存。数据库已经重建以排除旧基准死元组；禁用客户端 prepared statement cache，避免不同实验参数污染执行计划。未测磁盘冷启动、生产相册分布或负载SLO。

相册实际 keyset 页相对第三批路径，中位耗时约降低46%，Python分配峰值约降低95%；它包含额外的count/游标/URL序列化，SQL候选路径的数据另列，避免混用口径。

20路相同输入、100ms embedding替身的实测：

| 场景 | 替身调用次数 | 累计预算单位 | 整组耗时 ms |
|---|---:|---:|---:|
| 无合并 | 20 | 20 | 122.18 |
| 冷缓存合并 | 1 | 1 | 225.98 |
| 热缓存 | 0 | 0 | 41.77 |

冷缓存合并减少重复计算，但增加 Redis 协调耗时；热缓存才同时避免调用和等待模型。调用减少95%是重复输入场景的替身实验，不能换算成生产账单降幅。实际 token 延续第三批供应商计量，未提供币价或虚构人民币费用。独立用户不共享缓存结果。

## ANN 选择

默认 `SEARCH_ANN_ENABLED=false`。6000行测试中，普通计划选择用户索引加精确排序，召回对照为1.0。强制 HNSW 的3000条用户/Top-20场景，ef40最低召回0.70，ef200也只有0.90；30条稀疏用户/Top-20场景，ef200约34ms，精确约7ms且召回更完整。提高ef没有达到本切片“保持精确基准结果”的门槛，因此不默认启用，也不贸然重建索引或改m/ef_construction。

实现了可关闭的 ANN 路径：仅普通语义检索可启用；select、完整集合和结构化集合仍走精确路径；pgvector低于0.8回到精确路径。迭代扫描使用strict_order，ef_search默认200、max_scan_tuples默认20000，均为事务局部配置。近似返回不足候选上限时用精确查询确认，避免误报耗尽；取满候选也保留截断标记。生产路径不强迫查询规划器选 HNSW。强制关闭sort/bitmap/seqscan仅用于基准实验。

参数行为及“过滤可能减少ANN结果、需要用精确搜索对照”的依据：[pgvector官方文档](https://github.com/pgvector/pgvector#iterative-index-scans)。当前选择是按测量保留精确检索，后续使用真实向量和更大相册重新评估。
