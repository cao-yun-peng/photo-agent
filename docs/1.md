可以。结合你上传的这个 `agent_eval.py` 来看，TC-001 就很好理解了：**JSON 里的 TC-001 是“标准答案/考试题”，`agent_eval.py` 是“监考+判卷程序”，真正的 PhotoAgent 是“考生”。**

而且这里一定要区分两种模式：`replay` 是按照数据集给出的标准动作直接回放，用来检查评测程序本身；`real` 才是真正让 DashScope 模型自己决定调用什么工具，因此只有 `real` 的结果能反映模型能力。代码开头已经明确说明这一点。

下面就拿你这个 TC-001 从头走一遍。

# 6. Agent 到底调用了什么工具，怎么知道？

这里用了：

```python
ToolCallInterceptor
```

也就是一个**工具调用记录器**。

Agent 每真正调用一个工具，它都会记录：

```python
{
    "tool": tool_name,
    "arguments": ...
}
```

然后保存到：

```python
self.calls
```

例如 Agent 正确调用：

```text
search_photos(query="猫")
```

就会记录下来。

如果 Agent 错误调用：

```text
apply_skill(...)
```

也一样会留下记录。



最后：

```python
result.tool_calls = list(interceptor.calls)
```

因此评测器知道：

> **模型实际干了什么。**

# 8. 第一项：`expected_tools` 测工具选没选对

标准答案：

```json
"expected_tools": [
    "search_photos",
    "final_answer"
]
```

假设模型实际：

```text
search_photos
→ final_answer
```

那么工具选择正确。

但这里有一个细节：

```python
CONTROL_TOOLS = {"final_answer"}
```

在计算工具选择分的时候，会把 `final_answer` 排除掉：

```python
expected_counts = Counter(
    t for t in expected if t not in CONTROL_TOOLS
)

actual_counts = Counter(
    t for t in actual if t not in CONTROL_TOOLS
)
```

所以 TC-001 真正用于“工具选择评分”的核心其实是：

```text
expected = search_photos
actual   = search_photos
```

完全一致：

```text
score_tool_selection = 1.0
```

 

---

# 9. `tool_order_strict: false` 表示不严格检查顺序

TC-001：

```json
"tool_order_strict": false
```

代码是：

```python
if expected.get("tool_order_strict"):
    ...
else:
    result.score_tool_order = 1.0
```

所以这一条用例**不要求严格比较工具顺序**。

直接：

```text
score_tool_order = 1.0
```



对于 TC-001 这种只有一次搜索的简单用例，确实没必要强调复杂的顺序关系。

---

# 10. `must_not_call` 检查有没有干错事

TC-001：

```json
"must_not_call": ["apply_skill"]
```

意思是：

> 用户只是让你找猫照片，绝对不能擅自开始改照片。

代码：

```python
must_not_call = set(
    expected.get("must_not_call", [])
)

violated = must_not_call.intersection(actual_tools)
```

假设实际调用：

```text
search_photos
final_answer
```

没有 `apply_skill`：

```text
score_must_not_call = 1.0
```

但假设模型错误地：

```text
search_photos
→ apply_skill
→ final_answer
```

就会：

```text
score_must_not_call = 0
```

并记录：

```text
违规调用工具: ['apply_skill']
```



所以 TC-001 的 D1 意图识别实际上通过两个方向来测：

```text
应该做什么：
search_photos ✓

不应该做什么：
apply_skill ✗
```

这就比只检查有没有调用 `search_photos` 更严格。

# 11. TC-001 没有 `parameter_checks`

你会发现 TC-001 没写：

```json
"parameter_checks": {...}
```

所以它**不严格测试 `search_photos` 的 query 参数到底是不是“猫”**。

代码：

```python
checks = expected.get("parameter_checks", {})

if checks:
    ...
else:
    result.score_parameter = 1.0
```

因此 TC-001：

```text
score_parameter = 1.0
```

直接通过。

这也符合它的定位：

```text
dimension = D1
category = 搜索意图
```

它主要考：

> 能不能判断“这是搜索”。

而不是主要考：

> `query` 参数构造得精不精确。

后面 D3 的 testcase 才会重点检查参数。

## 最关键的是理解三组字段的分工

你可以把 TC-001 简化理解成：

```text
user_query
= 给模型出的“题目”

context
= 给这道题搭建的“测试环境”

expected
= 机器可以读取的“标准答案”

rubric
= 人能看懂的“评分说明 + 通过线”
```

其中 `photo_library` 又相当于：

```text
测试使用的模拟相册数据库
```

所以 TC-001 并不是直接拿 `"matching_photos": ["p-001"]` 判断模型“搜对没搜对”。在你当前这套代码里，它更准确地说是在测试：

> **模型面对“帮我找一下猫的照片”时，是否自主选择 `search_photos`；一旦选择了这个工具，评测环境按照 TC-001 的 `matching_photos` 确定性地返回 p-001；随后再根据 `expected` 对模型的工具选择、禁止行为、最终状态和结果内容进行打分。**

这也是为什么文件开头说，`real` 模式主要衡量的是 **Agent 决策能力，而不是底层数据库/向量检索本身的搜索质量**。
