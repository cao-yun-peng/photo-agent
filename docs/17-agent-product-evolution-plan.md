# Photo Agent 产品与 Agent 优化方案

日期：2026-09-06。来源：本任务中两轮优化讨论及用户要求整理方案的指示。

本文定义设计与实施顺序，不记录实时完成状态。唯一执行状态见 `.project-to-act/PROJECT_PROGRESS.md`。本次仅交付方案，未实现下述新增能力，不改变阶段 6 revision 4 或发布 Gate。

## 1. 目标与优先级

将项目完善为能够理解反馈、管理照片、使用可上传 Agent Skill 修图的助手。保留现有 FastAPI、PostgreSQL/pgvector、Redis/ARQ、Web、小程序和单 Agent 架构，渐进改造。

用户明确提出的两条近期主线：

1. 导入包含 `SKILL.md`、规范和参考图的修图 Skill，完成原图理解、创作方案、受确认生成与结果检查。
2. 前置识别用户意图和结果反馈，在同一搜索目标下连续两批结果遭到不满时升级检索策略，支持线索范围和全相册浏览。

前一轮建议保留为后续主线：旅行照片成组挑选、相册保存、交互调整与撤销。该场景排在上述两项之后，不把它当作用户已优先选择的首个功能。

总体效果通过任务完成率、用户纠正次数、结果质量、恢复正确性、延迟和成本评估。不给出未经基线验证的提升百分比。

## 3. 目标架构与状态归属

```text
Web / 小程序：对话、照片选择区、方案预览、确认、进度、撤销
                         ↓
Turn Resolver：意图、搜索关系、结果反馈、指代解析
                         ↓
策略与任务运行器：允许动作、步骤、预算、确认、检查点、恢复
                         ↓
单 Agent：短计划、按需取证、选择动作、有限重规划
                         ↓
领域能力：搜索 / 范围浏览 / 相册 / Skill 导入与执行 / 图像生成
                         ↓
已有数据库、对象存储、模型适配器与异步 Worker
```

明确数据所有者，避免多个模块自由改同一份字典：

- `Session`：聊天容器和任务引用。
- `Task`：跨轮次目标、约束、选择集合、待确认方案、进度与检查点。
- `Run`：一次执行的截止时间、调用预算、取消和 Trace。
- `SearchPlan`：查询条件、排序、候选及游标；沿用现有搜索服务契约。
- `Generation`：确认、额度、幂等、供应商执行和结果版本。

先用类型化契约建立边界，再在新增长任务确有需求时落库。不要第一步同时重写全部状态、API 和 Worker。

## 4. Prompt 与上下文工程

1. 将稳定职责、任务能力说明、工具说明、工作状态和照片证据分开。
2. 同一能力配置生成工具集合和对应 Prompt；明确普通文本结束与 final_answer 的统一约定。
3. 只有状态允许的工具才向模型开放，服务端仍再次执行授权和参数验证。
4. 权限、重试次数、预算、生成确认、可放宽条件由代码拥有，不靠重复 Prompt 规则实现。
5. 按需加载照片详情、Skill 规范和参考图，默认上下文仅含必要摘要与标识符。
6. 结构化记忆保存目标、硬/软约束、已选照片、反馈和待办；历史摘要作为补充，不承担唯一事实来源。
7. 输入中的照片描述、用户文字、上传 Skill 均为数据；不能提升为系统权限。
8. 版本化 Prompt、工具 Schema、模型和策略，记录在运行证据中。
9. 用户进度采用“正在比较候选照片”等状态摘要，不转发供应商隐藏推理字段。

验收：两个 Agent variant 均无引用不存在工具的规则；准备生成不显示为已入队；含 reasoning_content 的模拟响应不进入 SSE、最终回复和持久会话；长对话后仍保留有效目标与关键纠正。

## 5. 反馈驱动搜索和分级兜底

### 5.1 前置识别契约

在现有 TurnPlan 上增加类型化反馈字段，建议包括：

- `intent`：搜索、选择、修图、浏览、能力咨询等。
- `relation`：new / refine / replace / continue。
- `feedback_kind`：none / satisfied / reject_item / reject_batch / insufficient / unclear。
- `target_result_batch_id`、明确的 `photo_ids`、反馈原因和可提取的条件修正。
- `requested_scope`：继续匹配结果、浏览线索范围、浏览全相册。
- 来源与置信度；规则处理明确表达，模型只处理需要消歧的场景。

识别器描述用户表达，策略层决定调用工具。关键词情绪命中不能直接触发清空筛选。

### 5.2 状态和计数

按搜索任务维护 `search_goal_id`、最近展示批次、已计数反馈事件、连续整批不满次数、当前策略级别、有效约束与拒绝照片集合。

- 两次指不同结果批次上的有效整批负反馈；同一批多次抱怨、网络重放和重连不重复计数。
- “还有吗”是续看，“第三张不要”是单张排除，“不够多”是数量反馈，默认均不算整批不相关。
- 新目标或 replace 重置；同一目标的 refine 保留，满意或明确完成时清零。
- 无法判定反馈目标时不计数；能安全继续时继续，只有影响动作的歧义才澄清。
- 用户未明确拒绝具体照片或整批内容时，不擅自扩大照片排除集合。

### 5.3 工具策略

| 条件 | 动作 | 用户可见结果 |
|---|---|---|
| 初次搜索 | 按现有 SearchPlan 检索 | 匹配结果、覆盖与核验状态 |
| 第一次整批不满 | 利用原因调整召回/核验；只放宽允许的软条件 | 新批次与简短调整说明 |
| 第二次新批次仍不满 | 进入线索相册或时间线浏览 | 明确说明是范围候选，不是已确认匹配 |
| 线索浏览仍无帮助 | 提供进入全部相册的入口；用户选择后切换 | 分页全相册供人工寻找 |
| 用户直接要求全相册 | 直接浏览 | 不要求先累计两次不满 |
| 零结果但无用户反馈 | 依据覆盖率和预算执行既有确定性恢复 | 不冒充用户不满，不轻率声称相册没有 |
| 模型故障或索引不全 | 技术降级或索引提示 | 与语义不匹配分开记录 |

建议能力语义：搜索照片、继续结果、调整搜索、浏览线索范围、浏览全部相册。内部实现复用 SearchService 和稳定分页；不必一次性向模型公开所有能力。

全量兜底表示分页访问范围，不表示把全库照片载入内存或交给模型。所有权、硬排除、预算、旧代次保护和完整性标志继续生效。放宽条件必须反映在返回状态和文案中。

验收必须覆盖：两批触发升级、同批不重复计数、单张拒绝不升级、新目标重置、直接浏览绕过计数、技术失败不计数、硬约束不丢失、旧批次晚反馈不污染新目标。

## 6. 可上传修图 Agent Skill

### 6.1 样例与兼容范围

首个样例位于 `E:/project/agent/photo-to-organic-knit-main/photo-to-organic-knit-main/photo-to-organic-knit/`。

该包包含 SKILL.md、references/style-spec.md、assets/style-reference.png 和 agents/openai.yaml。流程包含原图观察、保留/转化/舍弃、创作方向、参考图角色、生成、检查与迭代。仅增加 prompt_template 长度不足以完整适配。

首版支持 Markdown、声明式流程和图片资源的 ZIP 包。自动识别唯一 Skill 根；存在多个候选根时明确报告。保留旧模板 Skill，以类型区分模板与流程包。脚本、外部依赖和任意命令执行不在首版范围，不能静默忽略并声称完整支持。

### 6.2 导入流程与模型

```text
上传 ZIP → 校验与识别根 → 解析元数据和资源引用
→ 展示名称、封面、能力兼容性及不支持项 → 保存私有 Skill 版本
```

建议逻辑对象（实施时冻结具体 Schema）：

- `Skill`：身份、所有者、类型、展示信息、当前版本。
- `SkillVersion`：不可变原文、解析结果、内容哈希、支持能力和导入器版本。
- `SkillAsset`：版本内路径、类型、大小、哈希、存储标识和图片角色。
- `SkillExecution` 或任务关联：Skill 版本、源图版本、创作方案、生成结果和核验记录。

导入校验包括：路径越界、绝对路径、链接、重复归一化路径、解压后大小/文件数上限、文件类型和缺失资源。上传内容不能提供凭据或绕过运行器权限。保留包来源及许可证信息；私有导入不自动发布到公共 Skill 库。

### 6.3 执行链路

1. 用户选择照片和 Skill，读取版本化入口说明。
2. 按需读取风格规范、源图和参考图，明确主体图与风格图角色。
3. 生成结构化创作方案：方向、画幅、retain/transform/discard、概念、标题、约束。
4. 将包里的 ImageGen 操作映射到项目的模型适配器；校验多图、画幅、编辑能力等兼容性。
5. 形成实际生成指令、引用资源和费用摘要，冻结后等待用户确认。
6. 复用现有确认、额度预占、幂等、异步生成及失败释放机制。
7. 核验尺寸/方向等确定性条件；视觉模型辅助检查主体、风格、文字与参考内容误复制。
8. 展示结果和不确定项；每次迭代保存新版本。自动重生成仅在已授权次数和费用内执行，否则提出修改建议并等待确认。

模型不能满足必要能力时拒绝执行或让用户选择明确标注的降级方案；不得静默丢弃参考图。用户的无文字要求优先于样例的默认标题；中文标题不机械套用英文单词计数，应在创作方案中明确规则。

用户确认绑定 Skill、创作方案、资源和费用范围。确认后修改这些内容必须失效旧确认。供应商超时可能已经执行，沿用对账与幂等策略，不承诺外部调用恰好一次。

验收：样例包可导入并完整解析本地引用；旧 Skill 可继续使用；不支持能力有清晰反馈；源图和风格图不混淆；重放确认不重复入队；执行期间更新 Skill 不改变已冻结任务；原图不覆盖。

## 7. 照片管理、记忆与交互的后续扩展

### 7.1 旅行相册精选

场景：“整理上周旅行照片，挑 12 张，风景和合照都要，别太重复。”

新增相册/成员关系、近似重复组和可撤销变更；先检索候选，再根据清晰度、重复度和场景覆盖进行成组选择。去重和筛选优先确定性算法，模糊审美比较再使用视觉模型。候选不足时如实说明，不补造照片。

用户可替换第三张、增加合照、固定某张，随后保存相册。撤销只反转本任务拥有的变更，不覆盖后续人工编辑。首版不做自动永久删除，重复照片先提供整理建议。

### 7.2 三类记忆

| 类型 | 示例 | 范围 |
|---|---|---|
| 任务记忆 | 本次 12 张，至少 3 张合照 | 当前任务 |
| 明确偏好 | 旅行相册优先人物 | 用户可查看、修改、删除 |
| 照片事实修正 | 这是杭州，不是苏州 | 特定照片及版本 |

保留来源、时间、作用范围与冲突处理。一次拒图不升级为长期偏好。与已有行为画像分开，不用隐式点击权重覆盖用户明确要求。

### 7.3 产品界面

稳定的选片区与对话共用带版本的选择集合；分页时不改变已展示照片的引用身份。展示任务进度、创作预览、费用确认、生成历史及撤销入口。修图 Skill 导入优先完成 Web，再验证小程序对应选择和执行链路，不能把 Web 验证等同于小程序通过。

## 8. 新技术的引入条件

| 技术 | 实验落点 | 保留条件 |
|---|---|---|
| 按需上下文与 Skill 渐进加载 | 修图包规范、候选照片详情 | 质量不退步且上下文、延迟或可维护性有收益 |
| 结构化短计划与有限重规划 | 修图创作、旅行选片 | 复合约束满足率提升，额外调用受预算约束 |
| 可恢复执行、checkpoint、人工中断 | 长任务与确认后继续 | 重启恢复、取消和重复确认测试通过 |
| 生成后核验与有限修正 | 针织样例 | 视觉评分与人工复核校准，禁止无界迭代 |
| 轨迹驱动离线改进 | 路由和工具误用案例 | 固定保留集提升，不在生产自动改 Prompt |

LangGraph 作为新流程的可选对照原型，比较现有状态机与 checkpoint/interrupt 的实现成本和恢复行为后再决定。不把换框架作为前置条件。暂不引入多 Agent、工具搜索、任意代码 Skill、自动自我改写或新的向量数据库。

参考（此前讨论已核对官方来源）：[上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)、[人工中断](https://docs.langchain.com/oss/python/langgraph/interrupts)。这些是技术候选依据，不是本项目效果证明。

## 10. 评测与实验方法

沿用 [评测体系 V2](11-evaluation-plan-v2.md)，不新建平行评测系统：

- L0：Schema、导入、所有权、反馈计数、确认、预算、状态恢复等确定性测试。
- L1：意图/关系/反馈识别、槽位、不必要澄清率和危险路由错误。
- L2：多轮工具顺序、参数、策略升级、Skill 资源读取与正确停止。
- L3：固定相册的召回/准确率、覆盖、零结果、成组多样性和约束满足。
- L4：隔离账号 HTTP/SSE、上传、生成、断线恢复和客户端链路。
- 修图专项：方向、主体识别、风格符合度、参考图内容误复制、标题准确度；自动评分以人工样本校准。

每个实验保存数据版本/切分、当前代码哈希、Prompt/模型/工具版本、随机性参数、预算、延迟、用量及失败类别。Development 调试、Validation 选择阈值、Test 保留验证。Mock 证明流程，不能证明生成效果；历史合成性能不代表真实生产负载。

硬门槛：跨用户资源访问、未确认的付费动作、重复生效、硬约束静默丢失在受测场景中为零。质量与性能阈值先建立基线再冻结，未测项明确列出。
